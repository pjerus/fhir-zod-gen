### #42 — the registry answer was the opposite of the obvious one

The issue's suggested first step was to check whether `packages2.fhir.org`
serves the missing `us.nlm.vsac@0.18.0`. It does — and it makes no difference.
`fhir-package-installer@1.13.1`'s `getTarballUrl` returns the identical
npm-style `{registry}/{id}/-/{id}-{version}.tgz` in **both** branches of its
`isPrivateRegistry` check; the two branches are character-for-character the
same, a distinction that doesn't exist. packages2's real layout is
`/packages/{id}/{version}` → 302 → `/web/{id}-{version}.tgz`, which that URL
shape never reaches. **No `registryUrl` value fixes this**, so graceful
degradation is the entire fix, not half of it. Recorded in CLAUDE.md so nobody
re-derives it.

### #40 — the narrowing goes back where it belongs

A named-type reference now carries a field-local `.superRefine()` re-applying
whatever requiredness *that occurrence* states beyond the shared file's
consensus. Chosen over `.and()` (bad inferred types) and over per-variant
datatype files (file-count + naming work). 55 re-applied requirements across
15 files in us.core, 35/9 in r4.core, 2/1 in sdc, 0 in mcode.

Spot-checked against the **raw StructureDefinitions**, not just our own
pipeline: US Core Practitioner's re-applied set is `identifier.system`,
`identifier.value`, `name.family` — exactly what its differential states.

Deliberately shallow (top-level fields of the occurrence only). The nested
case has no evidence behind it and a real open question about which consensus
to compare against.

### #41 — measured first, then written

Census of all 266 distinct constraints in us.core + r4.core, weighted by the
158 markers us.core's output actually emits: `A.exists() or B.exists() [or …]`
is 63 of them. The apparent runner-up, the `field.matches('…')` family, is 35
distinct rules and **zero** emitted markers. So exactly one shape is
translated.

Three refusals are the load-bearing part, and all three are in CLAUDE.md now:
all operands resolve or the whole rule is abandoned; `severity: "warning"` is
never enforced; and a `value.exists()` operand is a **choice group** resolving
to its flattened `value[x]` variants — read as a plain key it would have
rejected every conformant instance in existence.

Enforced: 72 r4.core, 64 us.core, 55 mcode, 26 genomics-reporting, 4 sdc.

### A claim I had put in the docs was wrong

The FAQ and #48 both stated that `davinci-dtr`'s unresolvable
`davinci-crd#current` dependency costs real output — bindings that can't
expand, types falling back to `z.unknown()`. That was **inference, never
measured**. Measured, it is false:

- no file in DTR's 45 references a CRD canonical at all;
- the four binding warnings are mime types and ISO currencies, which have no
  enumerable content and degrade in every package;
- the 11 `z.unknown()` markers are `Questionnaire.item`/`value[x]`, and appear
  identically in US Core, whose closure is complete.

Also verified: `davinci-crd` 2.0.1 **and** 2.2.1 sitting in the cache does not
satisfy a `#current` dependency, so the workaround the docs recommended —
"generate davinci-crd alongside DTR" — did not do what it claimed. Corrected
in the doc and in a correction comment on #48, which drops that issue's
priority to "make the warning honest".

The lesson is the repo's own rule, applied to prose: a plausible claim about
behaviour is worth exactly as much as a measured one, which is to say nothing.

### #50 — a silent footgun, found by checking the advice before giving it

The docs were about to recommend generating several IGs. The CLI takes one
input, so that means several runs — and two runs into the same output
directory **silently overwrites the barrel**:

```
DTR alone:                    45 files
after CRD into the same dir:  60 files, index.ts exports 0 DTR profiles
```

Every DTR file is still on disk; nothing errors, at generation or at compile.
Anything importing from the barrel loses half its schemas silently. Filed as
#50 with three options — accepting multiple inputs in one run is the only one
that's actually right, since `emitPackage` already takes a list.

There is a subtler half: a shared datatype holds the consensus of its batch
(#34/#40), so the second run's `CodeableConcept.ts` may not be the first
run's. For DTR/CRD they're byte-identical — checked — but that is luck.

**Documented workaround, in force until #50: one output directory per
package.** Costs duplicated datatype files across directories, which is
harmless — they're independent modules.

## #50 fixed — the CLI takes several inputs

`fhir-zod-gen a#1 b#2 -o ./out` generates one batch: shared datatypes
reconciled across every input and emitted once, one `index.ts` covering
everything. `emitPackage` already took a list of schemas, so the work was
composing the sources (`compositeSchemaSource`, `compositeTerminologySource`
— both first-hit-wins on the **leftmost input**, so the result is predictable
from the command rather than from iteration order) and threading multiple
inputs through the CLI.

Two deliberate refusals:

- **Package identifiers can't be mixed with file paths** in one run. A file
  input has no closure to resolve base chains against, so combining them
  would mean resolving some documents against a source they aren't from.
- **A second run into a directory holding another batch's files** now errors,
  names the orphans, and exits 1. That was #50's actual complaint: the barrel
  is rewritten from one run's results, so the earlier run's files stayed on
  disk and vanished from `index.ts`, silently. `--force` writes anyway.

Only files carrying emit/'s own header count as ours, so a hand-written `.ts`
sharing the directory is neither reported nor touched.

Verified: DTR + CRD in one run → 60 files, barrel exports all 9 DTR profiles
*and* CRD's, one `CodeableConcept.ts`, `tsc --strict` clean over the set,
byte-identical across runs. Single-package output is **byte-identical to
before the change** — us.core diffed clean. Tests 243 → 259; the two guard
tests confirmed non-vacuous by stubbing the check to always pass.

Reversing the argument order changes only `index.ts`'s export ordering for
this pair — no schema file differs — but the ordering rule is documented
because it is load-bearing where closures genuinely disagree.
