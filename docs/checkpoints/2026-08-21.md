## 13:52 update — example validation landed, and it found real bugs

`main` @ `ae1cda5`, 155 tests. PR #25 merged: a validation harness that runs real
conformant example resources from IG `package/example/` directories through the
generated schemas.

**Result: 404/441 examples validate (91.6%).** All 37 failures trace to exactly
two genuine, root-caused bugs — now filed and **open**:

- **#23 (serious)** — elements bearing an extension slice resolve `array: false`
  instead of `true`. Real resources with extensions present get **falsely
  rejected**. 31/37 failures. Verified independently at runtime: a conformant US
  Core Patient carrying a `us-core-race` extension is rejected with
  `Expected object, received array`. That's the most standard US Core pattern
  there is.
- **#24** — a primitive element that also carries an extension slice emits as
  `z.object({extension})` instead of its real primitive type. 6/37 failures.
  Verified: `SDCQuestionnaireResponse.questionnaire` emits `z.object({...})`
  while the same field in `SDCQuestionnaireResponseAdapt` (no extension slice)
  correctly emits `z.string()`.

### Why this matters for the earlier numbers in this checkpoint

The metrics above (191/191 resolving, 233/233 compiling, 54 warnings) are all
still true, and all of them stayed green while these bugs were live. **Resolving
and compiling is not the same as being correct.** The fixture-based regression
suite couldn't catch this: `FixtureSchemaSource` deliberately excludes the
Extension type, so extensions mask to `z.unknown()`, which trivially accepts
anything. The bug only appears once Extension resolves for real against a full
package source.

Treat "191/191 + compiles clean" as a *pipeline integrity* claim, not a
correctness claim. The 91.6% pass rate is the correctness number.
